# 完整项目分工与验收计划

基线日期：2026-10-14。当前仅 FR-04 基础版已实现；此文是后续开发约定，不能当作已完成功能清单。每位成员负责自己功能的后端、页面接入、样例和测试，公共改动通过 PR 协商。

## 范围

面向学习者的小型 Python 代码质量分析工具。第一版统一支持一个同步独立纯函数，最多 200 行，功能说明最多 2000 字符，最多 10 条生成用例；沿用现有 AST 限制和 JSON 可表达的输入输出。输入可上传 `.py` 或粘贴，说明可选注释或手写。暂不做跨文件工程分析、自动安装依赖、自动改写源码、自动提交、账号系统和公网执行服务。

## FR-01：陈宏伟——代码问题定位

- 新增 `fr01/` 模块：先做确定性的 AST/规则检查，再结合代码与说明请求 AI 分析，输出文件、行号、问题类型、理由和证据。
- 每条发现区分 `rule` 与 `ai`，并区分已由规则发现的事实与待核查的推测；无法确定行号时标为待定位，不能编造位置。
- 页面展示可定位的问题列表，保留规则编号、模型与提示词版本；禁止执行源码完成分析。
- 验收：固定样例中的约定规则能命中正确行号；无问题样例不凭空生成规则问题；AI 超时、无效 JSON 或越界行号可解释地报错/拒收；源码不被修改。
- 交付：规则清单、结构化发现接口、页面列表、正确/缺陷/无效输入测试。由彭启诚评审。

## FR-02：彭启诚——可解释质量评估

- 新增 `fr02/` 模块：基于 FR-01 结果和可复算的评分规则，输出分项得分、扣分依据及总分；AI 只解释已有得分，不决定分数。
- 评分公式、重复问题去重规则、每项扣分上限公开；未完成分析时显示“未评估”，不能默认 100 分。AI 疑似问题独立提示，默认不计入确定性分数。
- 验收：同一组输入反复评分一致；人工算例与程序一致；解释中的分数、问题编号均可追溯；删除/新增一条确定性发现时按公开公式变化；模型解释失败仍能显示规则分数。
- 交付：评分规则 v1、评分接口、分项解释页面、公式与边界测试。由敖德太评审。

## FR-03：敖德太——改进建议与代码对照

- 新增 `fr03/` 模块：围绕 FR-01 具体问题给出改进原因、局部修改建议和前后代码对照，关联发现编号和源码版本。
- 仅展示建议；不覆盖用户源文件、不自动提交。代码片段必须能在对应版本定位；不适用或证据不足时说明原因。
- 验收：已知问题的建议能说明对应原因；原片段与输入一致；源码改变后旧建议标为过期；无效响应不显示伪造修复；保存前后源码哈希一致。
- 交付：建议接口、对照页面、固定问题样例、关联/版本/异常测试。由薛奕辰评审。

## FR-04：薛奕辰——AI 测试用例生成与验证

- 接管现有 `fr04/`、生成/运行接口和页面流程，完善与前三模块的联调，继续支持上传、说明来源选择、预览、确认、执行和报告。
- 生成预期依据需求；保留正常、边界和说明中明确的异常场景。不把 AI 预测当成真实执行结果，不按实际结果反改预期。
- 验收：固定 oracle 核对预期；已知错误边界能被发现；正确实现通过；需求变化后生成新版本且旧记录保留；确认前不执行；超时与失败均留痕。
- 交付：现有 51 项测试持续通过、模块新增回归测试、脱敏真实 AI 验收记录和完整链路报告。由陈宏伟评审。

## 里程碑与依赖

| 阶段 | 共同完成条件 | 可以并行的工作 |
| --- | --- | --- |
| M0 接口与判据 | 四人确认 INTERFACES.md、评分规则、固定样例的独立预期 | 各模块建立自己的分支和测试文件 |
| M1 各模块可验收 | 每个模块有 API/页面/测试；使用明确标注的固定输入完成单模块联调 | FR-02/03 使用固定的 FR-01 结果样例；FR-04 继续独立改进 |
| M2 串联 | 上传→定位→评分→建议→生成→确认→运行→报告可走通，所有步骤对应同一输入版本 | 分别修复模块错误；公共入口变更排队合并 |
| M3 提交与展示 | CI 通过，真实模型验收留痕，正确与已知缺陷两类样例均演示，文档更新 | 汇总报告、录制演示、互相复核 |

具体日期在组内课表确定后补充，不把阶段名称当成截止时间。FR-02/03 不必等待 FR-01 全部写完，但固定输入不能在正式模式伪装成真实分析结果。

## 共用验收原则

每条结论都回答：输入是哪一版、依据是什么、如何独立核对、失败如何显示。AI 的格式合法、可执行、发现已知缺陷和与需求一致分别验证，不能只统计“测试通过率”。真实模型有波动，对固定样例至少重复三轮，保留成功与失败，不挑选最好的一次。通过这些检查只支持当前范围内的验收，不宣称证明所有代码正确。
